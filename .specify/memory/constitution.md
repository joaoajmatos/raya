# Raya Constitution

## Core Principles

### I. Laya Is the Specification

Raya-L MUST reproduce the behavior of the pinned Laya reference (`reference/laya-sparse/`, a git
submodule) for the same weights and inputs: sequence layout, marker-token attribution, truncation and
padding, layer and attention patterns, decision head, and temperature-calibrated probabilities. Where
Laya's behavior looks accidental or underspecified, Raya MUST match it and report the observation; it
MUST NOT silently fix it. Behavior changes are allowed only through a feature specification that names
the divergence. Files under `reference/` and vendored fixtures MUST NOT be edited by hand.

### II. Parity Is Proven by Golden Fixtures

Every numerical or behavioral claim of equivalence MUST be checked against fixtures generated by Laya
(`artifacts/raya-golden/`, vendored into `tests/data/` with the laya-sparse commit recorded in each
`meta.json`). Checks MUST localize failures (by layer index, tensor name or case), and tolerances MUST be
stated and justified. Fixtures are regenerated, never hand-edited. Tests MUST run offline with no network
and no real checkpoint unless explicitly marked slow.

### III. Measure, Do Not Assume

Performance claims MUST come from a reproducible run that records CPU model, core count, feature flags,
thread settings, rustc version, git commit and checkpoint revision. Numbers produced on any machine other
than the project's target CPU (the i7-8700 of the feasibility study) MUST be labeled "cloud-agent hardware,
indicative only" and MUST NOT be compared with `docs/feasibility.md` or Laya result directories.
Unmeasured statements are hypotheses and MUST be labeled as such. Negative and inconclusive results are
valid outcomes and MUST be reported.

### IV. Scope Discipline: Raya-L, fp32, Inference Only

Until Phase 2 results exist, Raya implements only Raya-L: Laya's exact shape, fp32 arithmetic, CPU
inference. Compression, architecture variants, training, and int8/fp16/bf16 paths MUST NOT be built.
Low-precision weights MAY be converted to fp32 on load. `docs/feasibility.md` is the source of truth for
scope; a change of scope is a constitution or feasibility amendment first, a feature second.

### V. Portable First, SIMD Optional

The target CPU and precision are an open decision. The project MUST NOT choose a SIMD target: a portable
path MUST always exist and be the default, and AVX2, NEON or other micro-kernels MUST be optional cargo
features with runtime dispatch and a portable fallback. `unsafe` is permitted only in `raya-kernels`;
every other crate MUST forbid it. The project MUST build and pass tests on Linux x86_64 and macOS arm64,
and Windows builds MUST be supported for the researcher's measurement machine.

### VI. Correctness Before Speed, Reference Before Kernel

An unoptimized, verifiably correct implementation MUST exist before any optimized one, and every
optimized kernel MUST be tested against a naive oracle with identical mask semantics. Attention is invoked
through a single kernel trait so implementations are interchangeable without touching model code. A
benchmark MUST NOT run against a model whose output parity with Laya has not been checked on the same
input. Speed claims MUST account for the whole forward pass, not only the kernel.

### VII. Small Surface, Explicit Errors

Dependencies are limited to those a specification names. Unsupported configurations MUST return
`Error::Unimplemented` (or an equivalent explicit error) rather than degrade silently. Weight loading
MUST fail loudly, naming missing, unused and mis-shaped tensors. Comments are sparse and explain why, not
what.

## Technical Constraints

- Language: Rust stable, edition 2021, toolchain pinned by `rust-toolchain.toml`.
- Workspace crates: `raya-core`, `raya-kernels`, `raya-weights`, `raya-tokenizer`, `raya-cli`.
- CI: fmt, `clippy -D warnings`, tests on ubuntu-latest (x86_64) and macos-14 (arm64), and a dependency
  audit.
- Python-side work (golden fixtures, tokenizer goldens, the `compare-raya` command) lives in
  `laya-sparse` and is bridged into Raya by vendoring output, never by importing code.
- Generated results (`results/`, `target/`) are git-ignored. Model weights, caches and credentials MUST NOT
  be committed. Fixtures committed to Raya MUST stay small (tiny fixture model only).

## Workflow

- Each feature follows specify, plan, tasks, implement under `specs/NNN-name/`, on one branch and one PR.
  Dependent features start only after their dependencies are merged.
- Read `README.md` and `docs/feasibility.md` before changing anything. If a file a task names is missing,
  stop and say so; if an ambiguity blocks progress, record the question in the PR description instead of
  guessing.
- Every change ships with tests. The PR description states what is done, what is not, and any divergence
  from the specification.
- Decisions the feasibility study leaves to humans (target CPU and precision, whether Rust beats the
  PyTorch block-local kernel, compression and training) MUST NOT be settled inside an implementation
  feature.

## Governance

This constitution governs specifications, plans, implementation and review. Reviews MUST check
compliance with the applicable principles and record deviations. A feature that conflicts with a
principle MUST resolve the conflict through an explicit amendment first.

Amendments state their rationale and affected principles, update `docs/feasibility.md` when scope
changes, preserve the ratification date, and bump the version: MAJOR for incompatible governance changes,
MINOR for new or materially expanded principles, PATCH for clarifications.
